# M10 Stage 2 — Bounded live evaluation

Date: 2026-10-30. CEO approval was received for at most three sequential calls, no retries, existing Qwen only, and a 60-second per-call limit. No applications were closed; Windows settings and model/context/output configuration were unchanged. Calls used `qwen3.5:2b-q4_K_M`, context 4096, output limit 2048, timeout 60 seconds. Evidence files and isolated validation database are under ignored `data/m10-stage2/`.

## Scope and safety

Two calls were made: one Orion structured planning request and one Orion-provider numerical-copy request. Both returned before the timeout. A third research synthesis call was **not performed**. Available research records had only publication metadata and short repository descriptions, with no meaningful abstracts, full papers, README excerpts or code evidence. The CEO approval explicitly conditioned synthesis on richer verified evidence. No replacement or fabricated sources were used. No applications were closed, no code generated by the model was executed, and no project plan was approved or executed.

The planning call was saved in the separate database `data/m10-stage2/validation.sqlite3`; its plan `b9e802e0-057c-4525-8e0f-add900d0459e` remains proposed. The numeric call used Orion's existing provider interface and its response is saved at `data/m10-stage2/numerical.json`.

## Results

### Structured planning

Orion accepted and persisted the model response as a schema-valid proposal. It included environment, database, UI, LLM integration, database integration, application integration, testing and packaging tasks. It left the proposal unapproved as required.

The model still made errors despite the updated planning instructions. The UI and database were treated as separate tasks, but application integration depended only on the UI task; it omitted the database and LLM integration prerequisites. The LLM integration task depended on UI design rather than the setup/model prerequisite. Some criteria were concrete file names or scripts, but others were circular or subjective, such as requiring the test task to meet its own criteria. It also assumed administrative privileges and implied Python/SQLite installation without evidence. It correctly kept test and packaging after application integration and distinguished RAM, VRAM, model size and context as separate terms, but its claim that hardware would support the model was an assumption, not a measured conclusion.

Outcome: valid structured proposal, incomplete dependency graph and mixed acceptance quality. No task was created.

### Numerical fidelity

The fixed input gave `repository:866513204` (LightRAG) 5,738 forks and `repository:778431525` (GraphRAG) 3,867 forks. The model returned both integers correctly. It returned repository names rather than the requested stable ID in `graph_rag_source_id`, and placed the LightRAG name in the field called `distinction`. Therefore the numeric values were right while requested identifier/field semantics were not fully followed. This is one deliberately bounded sample, not proof of general numeric reliability.

### Research synthesis

Not performed. The available verified packet remains too thin for a useful analytical comparison, and the CEO's explicit condition was unmet. The previous M9 invalid `limitations` citation and incorrect GraphRAG count remain preserved unchanged as regression evidence. No live synthesis quality improvement is claimed.

## Comparison with M9 baseline

M9 used a different prompt and one four-record metadata-only synthesis: it invented source ID `limitations`, misstated GraphRAG as 38,672 forks, miscounted sources, and compared repository popularity with publication records. M10's deterministic software change now enumerates packet IDs in the provider's structured schema while retaining the independent verifier. That protection was covered offline; Stage 2 did not run synthesis, so its effect on actual model citation behavior is unmeasured.

M10 planning instructions are more explicit. The single live proposal still omitted dependencies, so this sample does not demonstrate improved dependency completeness. The numerical test is only partially successful: the two counts were reproduced exactly but the required stable source identifier was not.

Prompts, request types, evidence and sampling differ. These observations are descriptive, not a controlled benchmark and do not establish a causal improvement.

## Assessment and next step

The offline improvements make invalid source IDs harder to generate and make planning expectations clearer. Live results confirm that schema validity is not enough: one planning proposal remained dependency-incomplete, and a short numeric response copied figures but missed field semantics. The next useful step is to collect richer source material through Orion's normal approved research workflow, verify it, and then request a fresh CEO approval for one bounded synthesis. Continue to retain human review for task graphs and factual claims. The local 2B model is not demonstrated as a dependable research analyst.
